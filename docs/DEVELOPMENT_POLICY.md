# 课刻开发与发布规范

本文适用于课刻仓库后续的维护者、贡献者、GPT、Codex 与其他自动化开发工具。它定义 `1.0.0` 之前的产品推进、缺陷分级、安全工作、版本号、路线图、PR、测试、隐私和发布规则。

路线图可以根据真实用户反馈调整；调整时应更新本文，而不是让并行分支各自形成不同规则。

## 1. 最高优先级：持续交付用户价值

> 课刻当前处于快速产品迭代阶段。主线优先级是持续交付用户可感知的新能力，而不是无限进行理论审计、无边界重构或低收益缺陷修复。

安全、稳定性和代码质量仍然重要，但必须服务于产品推进。不能因为存在非阻断性问题，就无限延后下一阶段功能。

默认决策顺序：

1. 立即处理 P0。
2. 修复阻断当前版本的 P1。
3. 推进当前版本的用户目标和端到端流程。
4. 记录并安排 P2。
5. 集中批量处理 P3。

## 2. 缺陷分级

### P0：立即阻断

满足任意一项即为 P0：

- 数据丢失或数据损坏；
- 可实际利用的严重安全问题；
- 安装包无法安装；
- 应用无法启动；
- 升级导致用户数据被删除；
- 核心流程必现崩溃；
- 发布包包含不应存在的外部执行能力。

处理方式：

- 立即停止发布；
- 优先修复；
- 必须增加回归验证。

### P1：阻断当前版本

典型情况：

- 当前版本的主要卖点不可用；
- OCR、Excel 导入、保存等核心能力大面积失败；
- 明确可复现的卡死；
- 主流 Windows 环境无法完成核心流程。

处理方式：

- 阻断当前 Beta 或正式版；
- 修复到主要流程可用即可；
- 不要求同时解决所有边缘输入。

### P2：不阻断主线

典型情况：

- 少数学校或特殊课表格式不兼容；
- 边缘 DPI、窗口位置或显示问题；
- 可恢复的错误提示不够清楚；
- 非核心交互瑕疵；
- 低概率异常。

处理方式：

- 记录 Issue；
- 排入后续补丁或专项版本；
- 不得因此无限延迟主要功能。

### P3：集中处理

典型情况：

- 文案；
- 像素级样式；
- 低价值清理；
- 不影响功能的重命名；
- 理论上的代码完美化。

处理方式：

- 集中批量处理；
- 不为单个 P3 问题频繁创建发布版本。

## 3. 安全工作的停止条件

1. 发现具体、可验证的权限越界或危险执行路径时必须修复。
2. 修复后需要有对应静态测试、编译验证或最小运行验证。
3. 已知问题封口后，不继续进行没有明确风险假设的泛化审计。
4. 不以“还没有证明绝对安全”为理由长期阻塞功能开发。
5. 完整恶意 WebView、模糊测试或高级攻击验证可以作为独立安全专项，不应混入普通功能版本。

安全工作的目标是：

```text
消除明确风险，而不是证明软件绝对无风险。
```

任何安全结论都应说明证据边界。例如，静态策略测试、编译通过、安装包启动 smoke test 与完整运行时攻击验证不是同一层级，不得互相替代或夸大。

## 4. `1.0.0` 前的版本号规范

课刻在 `1.0.0` 前遵循语义化版本的预发布规则，并以用户可感知范围决定版本，不以提交数量决定版本。

### Minor 版本：`0.x.0`

适用于用户可以明显感知的新能力、新平台或主要体验升级。

当前版本主题示例：

```text
v0.1.0  首个公开 Windows Beta / MVP
v0.2.0  课表管理能力
v0.3.0  编辑与设置体系稳定
v0.4.0  课刻品牌与桌面体验
v0.5.0  本地截图识别
v0.6.0  macOS 支持
```

### Patch 版本：`0.x.y`

适用于：

- 修复当前正式版本；
- 不新增主要用户能力；
- 修复兼容性、崩溃、安装、数据或交互问题。

例如：

```text
v0.5.1
v0.5.2
```

### Beta 版本：`0.x.0-beta.n`

适用于：

- 新能力已经形成完整安装包；
- 核心流程可以使用；
- 仍需要真实用户样本和环境验证；
- 已知限制已经写明。

例如：

```text
v0.5.0-beta.1  首个原生截图识别测试包
v0.5.0-beta.2  修复大图、并发和模型加载问题
v0.5.0         正式截图识别版本
```

### 版本禁止事项

- 不根据提交数量随意升级 minor 版本；
- 不因为单个 Bug 升级 minor 版本；
- 不修改、删除或重新指向已经发布的 tag；
- 不重新上传不同内容但使用相同版本号的安装包；
- 不让开发安装包继续使用已经公开发布的版本号；
- 已发布 `v0.4.0` 后，新的测试安装包不能仍显示为 `0.4.0`；
- 发布准备之外，不在普通功能或文档 PR 中顺手修改版本号。

版本发布时，`package.json`、`src-tauri/Cargo.toml` 与 `src-tauri/tauri.conf.json` 必须一致。

## 5. 当前路线图

路线图以真实用户反馈为最终依据，可以调整，但 Windows OCR 与 macOS 基线不强行捆绑。

### 当前安全边界封口：PR #93

目标：

- 只处理已经明确发现的最后一个权限边界问题；
- CI 通过；
- 完成一次基本 Windows 人工验证；
- 合并后停止扩大该专项。

本规范 PR 不修改 PR #93 的分支，也不重复处理其运行时权限、CSP、Release OCR 边界或工作流修复。

### 下一主线：`v0.5.0-beta.1`

主题：

```text
本地课表截图识别 + 导入审查
```

承载 PR：

```text
PR #91 / spike/rust-native-ocr
```

PR #93 合并后，PR #91 应基于最新 `main` 整合明确的运行时能力和安全边界，但不得重新引入 Release 系统 Python、环境选择的外部执行路径或前端猜测能力可用性。

Beta 发布标准：

- 安装包可正常安装和启动；
- Excel 导入不回归；
- 常见课表截图可以进入识别和审查流程；
- 不无限卡死；
- 模型缺失、初始化失败和图片过大时有明确结果；
- 不发生数据损坏；
- 已知识别限制写入 Release Notes。

不要求：

- 所有学校课表都识别正确；
- 所有特殊图片都支持；
- OCR 在发布前达到理论完美；
- 所有非阻断问题全部清零。

### 后续主线：`v0.6.0-beta.1`

主题：

```text
macOS 基线支持
```

承载 PR：

```text
PR #92 / feat/macos-baseline
```

macOS 不与 Windows OCR 强行捆绑在同一个版本中。macOS 构建成功只证明打包链路可用；正式推进前仍需真实 Mac 上的窗口、托盘或菜单栏、Excel 导入、持久化、Retina、多显示器与升级验证。

## 6. 功能阶段的范围控制

每个功能阶段开始前必须明确：

```text
必须完成
可以延期
明确不做
```

### OCR Beta 范围示例

#### 必须完成

- Release 内置或可正确初始化的 OCR 后端；
- 超时和失败能够返回；
- 图片尺寸和资源使用有边界；
- 识别结果进入人工审查；
- 不直接覆盖用户原有课表；
- 真实安装包可以运行。

#### 可以延期

- 极端模糊图片；
- 所有学校格式；
- 所有教师、地点字段达到满准确率；
- 自动修正全部 OCR 错字；
- 完整运行时恶意 IPC 测试。

#### 明确不做

- 云端 OCR；
- Release 依赖系统 Python；
- 未经用户确认直接修改课表；
- 为追求指标而增加不可维护的特殊样本硬编码。

范围变化必须在 PR 描述或 Issue 中明确记录。发现 P2、P3 时，优先登记，不应自动扩大当前 PR。

## 7. PR 开发规范

1. 一个 PR 只处理一个明确主题。
2. 不把无关重构、格式化和功能混入同一个 PR。
3. 已有 PR 能承载修改时，不新建重复 PR。
4. 不在未经要求的情况下合并 PR。
5. 修改现有 PR 前先确认：
   - base；
   - HEAD；
   - Draft 状态；
   - 是否有并行分支冲突。
6. 功能 PR 应包含：
   - 用户目标；
   - 实现范围；
   - 明确不做什么；
   - 验证结果；
   - 已知限制；
   - 后续工作。
7. 不使用“完全安全”“彻底无风险”“支持所有格式”等无法证明的表述。
8. 测试和文档必须描述真实覆盖范围，不夸大 smoke test、静态测试或 CI 的能力。
9. 开始修改前以最新目标分支为准；不要把 `spike/rust-native-ocr`、`feat/macos-baseline` 或其他并行分支无关内容带入文档或功能 PR。
10. 提交前检查差异和工作区，确保没有意外文件、生成物、锁文件或版本号变化。
11. PR 保持 Draft，直到其自身定义的退出条件满足；是否转为 Ready 或合并由维护者明确决定。

## 8. 测试规范

### 必须自动化

- 数据格式与迁移；
- 核心业务纯函数；
- 导入草稿结构；
- 权限分配静态策略；
- Debug / Release 编译；
- Web 构建；
- 安装包构建；
- 工作区无意外修改。

自动化测试应固定输入、输出和失败条件。网络、模型下载或外部服务相关测试应说明其可重复性和证据范围。

### 必须人工测试

正式发布或重要 Beta 前至少检查：

- 安装和卸载；
- 首次启动；
- 托盘显示与隐藏；
- 课表读取、编辑和保存；
- Excel 导入；
- 当前版本核心新功能；
- 多 DPI 或至少一个非 100% 缩放环境；
- 更新或覆盖安装时用户数据保留。

人工验证应记录使用的安装包、版本或 commit、系统环境和结果，不应只写“测试通过”。

### 不要求每个 PR 都执行

- 所有 Windows 版本矩阵；
- 所有显示器组合；
- 所有课表样本；
- 全量安全攻击测试；
- 完整长期稳定性测试。

这些项目可以在发布候选阶段或独立专项中执行。

## 9. 真实用户隐私

- 不要求用户公开完整课表、聊天记录、文件绝对路径或控制台日志；
- 请求日志时必须明确要求脱敏；
- 优先由应用或诊断脚本生成匿名诊断摘要；
- 默认移除用户名、学号、教师姓名、文件绝对路径、课表具体内容、设备标识和其他个人信息；
- GitHub Issue 模板必须包含隐私提醒；
- 测试样本进入仓库前，必须确认可公开使用或已经完成匿名化；
- 只收集复现问题所需的最小样例；
- 公开 Issue 中发现未脱敏内容时，应优先提醒用户删除或替换，不继续扩散原始内容。

匿名诊断摘要可以保留版本、错误类别、阶段、耗时区间、图片尺寸、模型状态和经过归一化的系统信息，但不得包含可还原用户课表或身份的原文。

## 10. 发布标准

### Beta 可以发布的条件

- 核心新能力能够完成一次端到端流程；
- 没有已知 P0；
- 没有阻断主要卖点的 P1；
- 安装包由 CI 生成；
- 版本号一致；
- Release Notes 写明已知限制；
- 提供校验值；
- 至少完成一次真实安装测试。

### 正式版可以发布的条件

- Beta 已经过真实环境测试；
- 主要反馈已经处理；
- 升级和用户数据保留得到验证；
- 核心流程稳定；
- 不要求所有 P2、P3 问题清零。

### 发布流程

1. 冻结当前版本的“必须完成 / 可以延期 / 明确不做”。
2. 仅在发布准备 PR 中统一更新版本号和面向用户的 Changelog。
3. 由 CI 从明确 commit 构建安装包，不使用本地未知产物替代。
4. 记录安装包文件名、大小、SHA-256、构建 commit 和测试环境。
5. 完成规定的人工安装与核心流程验证。
6. 编写面向用户的 Release Notes，并列出已知限制。
7. 创建新的不可变 tag 和 Release；预发布版本必须标记为 prerelease。
8. 发布后不得移动 tag、替换同版本安装包或重写历史 Release 内容来掩盖差异；修复应使用新 patch 或 beta 序号。

## 11. Release Notes 规范

Release Notes 不直接堆砌全部 PR 标题，应以用户为中心使用以下结构：

```text
本版重点
新增功能
体验改进
修复问题
升级说明
已知限制
文件校验
```

技术性的 PR 清单可以放在最后的完整 Changelog 中。

统一 Release 名称：

```text
课刻 vX.Y.Z
```

Windows 安装包建议命名：

```text
课刻_X.Y.Z_x64-setup.exe
```

Beta 示例：

```text
课刻_0.5.0-beta.1_x64-setup.exe
```

文件校验至少提供 SHA-256。升级说明必须明确用户数据保留要求、兼容性变化和需要人工操作的步骤。
